# 2026-06-01 session — Durable upload pipeline (Phases 1–4)

**Status:** Phase 1 deployed (migration 0018 + idempotent ingest + FOR UPDATE
+ min-instances=1). Phases 2, 3, 4 code-complete and merged into the
working tree, awaiting an EAS mobile build + on-water validation. Phase 5
(cleanup) deliberately deferred until two clean on-water races with the
native uploader prove the architecture works.

## What we worked on

A frustrated start ("it feels like we're moving further away from the
target end state") turned into a re-plan and four phases of focused work
on the recorder upload pipeline.

The 2026-05-31 on-water race ("Harmony Delivery") captured 2,090 GPS
points client-side but recorded zero mark passes, no `ended_at`, no
`ai_summary`. Cloud Logging revealed the failure: telemetry POSTs
arrived in bursts separated by long silences, with the last live batch
at 15:44:41Z (35 min into a race that should have run ~100 min), then
silence until a delayed dump at 18:32:16Z. The recorder's `useTrackRecorder`
JS-driven `setInterval(flushNow, 30_000)` flush loop doesn't fire when
the React Native JS bridge sleeps — phone screen off, app backgrounded.
Transistorsoft's native foreground service kept GPS *capture* alive (the
2,090-point count), but JS-owned uploads stalled silently. The
"ON LINE" label on the GuidanceCard turned out to be cross-track
distance to the next mark (navigation), not connectivity, so the UI gave
the user no signal that anything was wrong.

The diagnosis drove a four-phase comprehensive plan
(`2026-06-01_durable-upload-pipeline-plan.md`), all approved up-front:

1. **Phase 1 — Backend idempotency + FOR UPDATE + min-instances=1.**
   The unlock for everything after. With ON CONFLICT DO NOTHING on
   (session_id, recorded_at), the client can safely retry batches
   without creating duplicates. FOR UPDATE serializes mark-pass writes
   against concurrent batches. min-instances=1 kills the cold-start
   500 we saw at 15:33:09Z (8.24-second hung request, almost certainly
   Cloud Run scale-from-zero).

2. **Phase 2 — Recorder diagnostics.** A new `recorder_debriefs` table
   (separate, history-friendly), POST `/api/races/{id}/recorder-debrief`,
   an on-device ring buffer in AsyncStorage (`recorderLog.ts`), and a
   hidden debug screen reached by long-pressing the user-email pill on
   the home screen. The recorder POSTs the debrief blob best-effort at
   `stop()`. The whole point: the next failure is diagnosable without
   trawling Cloud Logging.

3. **Phase 3 — Visible upload-status badge.** Pure derivation
   (`uploadStatus.ts`) turning `LiveStats` + NetInfo + wall clock into a
   four-state status (Live / Buffering / Stalled / Offline). Small
   colored pill on the recording screen next to the LIVE chip — first
   honest connectivity indicator the recorder has ever had.

4. **Phase 4 — Transistorsoft native HTTP uploader, flag-gated.** The
   actual fix for the JS-sleep problem. Configures Transistorsoft's
   built-in http layer with a `locationTemplate` matching our wire shape
   and a `rootProperty: "gps"` envelope. JS-side token refresh keeps
   the bearer fresh via AppState + `onIdTokenChanged` + 30-min interval.
   Uploads keep flowing with the screen locked because the HTTP layer
   runs in native code. The `useTrackRecorder` hook becomes dual-mode;
   native mode observes `onHttp` events to update `LiveStats` + the
   ring buffer, polls `getCount()` for queue depth, and `flushNow()`
   becomes `BackgroundGeolocation.sync()`. Ships behind
   `featureFlags.ts::native_uploader`, default OFF, toggleable from the
   debug screen — if the locationTemplate body is wrong we can flip
   back without losing a race.

Three ops runbooks (Phase 1, Phase 2, Phase 3+4) document each step.

## Decisions and rationale

**Single comprehensive plan, all four phases up-front, approved
together.** The 5/30 session had shipped 20k LOC the night before the
5/31 race without on-water validation — the same pattern that's been
breaking us. Going broad on the plan first and narrow on each phase's
execution forced the conversation about what "shipped" means before any
code touched the wire. Phase 1 is structural, Phase 2 buys diagnostics,
Phase 3 buys visibility, Phase 4 is the actual fix. Approving them
together meant no surprise about the direction; executing them
sequentially with the ability to pause between phases meant no all-or-
nothing bet.

**Separate `recorder_debriefs` table, not a JSONB column.** Confirmed
with the user up-front: a race may have multiple recording sessions
(stop / restart, auto-stop edge cases); each deserves its own row with
its own `created_at`. Queries like "races with > 3 network errors this
month" become a clean WHERE against a single JSONB key, with the index
on `(session_id, created_at DESC)` answering "most recent debrief" in
one row read. Cost: one more migration. Benefit: history works from day
one without a future migration to extract.

**Phase 4 ships behind a feature flag.** The Transistorsoft
`locationTemplate` body shape is a known-unknown until it actually hits
our endpoint on a real device. If the template is wrong, every POST
422s silently and we're worse off than where we started. The flag
(default OFF, toggleable from the debug screen) means we ship both code
paths in one EAS build, flip on, watch the debrief; if the headline
numbers are bad, flip off and iterate without losing a race. The
backend's pydantic `field_validator` for negative sentinel coercion is
the other half of that de-risking — one fix that protects both
uploaders' resilience to missing-speed samples.

**Sentinel coercion lives in pydantic, not in the locationTemplate.**
Transistorsoft templates don't have a clean way to emit `null` vs.
numeric values conditionally. The backend coercing `<0` → `None` keeps
the wire shape simple and matches the JS uploader's behavior (which
already normalises to null in `normalizeLocation`). One server-side
change handles both code paths, present and future.

**Long-press on the user-email pill as the debug-screen gesture.**
v1 navigation, 1.5 s hold. Stable, hidden, won't catch a casual tap.
Phase 3 originally specced "5 taps on the LIVE pill"; long-press is
cleaner and doesn't fight the LIVE chip's accessibility semantics.

**"ON LINE" stays as a navigation label.** It's correct in its current
usage (cross-track distance to next mark, ±15 m). The fix for the
connectivity-mis-signal problem is to add a SEPARATE upload-status
badge — not to repurpose ON LINE. Phase 3 ships exactly that.

**`recent_log` shipped inline in the debrief blob, 50-entry cap.**
The trade-off: the full 200-entry ring buffer stays on device (for the
debug screen), but a 50-entry tail rides along with every debrief POST
so the server has enough to triage without the user navigating a
debug surface. 50 × ~200 bytes = ~10 KB per debrief, negligible.

**Recorder-debrief endpoint is INSERT-only, never UPDATE.** Insert-only
preserves history; "most recent" reads use `ORDER BY created_at DESC
LIMIT 1`. UPDATE would have been simpler but would have erased the
exact data we want when a session crashes-and-restarts.

## Technical debt flagged or accepted today

**Accepted, time-boxed.** The Phase 4 feature flag and the dual-mode
`useTrackRecorder` are deliberate transient complexity. Phase 5 deletes
both. If three on-water races pass without flipping the flag off, we
ship the cleanup; if not, we extend the dual-mode period to debug.

**Recorder coverage limitation, documented.** The Phase 2 ring buffer
records only what JS sees. With the JS uploader (Phase 1+2 baseline)
this means long quiet stretches in the log correspond to JS being
asleep, not to "nothing happening." After Phase 4 flips on, the
ring-buffer source switches to native `onHttp` events which fire
regardless of JS state — log becomes continuous. The
`recorderLog.ts` docstring documents this distinction so future
debuggers don't misread an empty middle.

**Backend pre-validator coerces all-negative sentinels.** Side effect:
a real GPS error returning -1 for a value we genuinely needed gets
silently nulled. Acceptable today because the alternatives (422 the
whole batch on any sentinel, or per-field client-side stripping in two
codebases) are worse. If we ever care about distinguishing "GPS
provider had no value" from "GPS error condition," we re-evaluate.

**IMU upload still not wired.** The heel gauge UI shows live IMU data
that flows into a queue that's never persisted past the wire boundary.
`heel_summary` is always empty. Phase 4's GPS focus is deliberate;
adding IMU to the native uploader is a follow-up after GPS is proven.
For now the gauge is misleading — fix or hide once GPS is stable.

**`useMarkPasses` + `useMissedMarkNotifier` polling still on,**
even though detection hasn't been validated on real water. Wasteful
API calls but not broken; the re-plan §8 shelved them pending a
working race recording. Re-evaluate after the on-water test.

**`track_points.session_id, recorded_at` had one duplicate row pre-
migration.** Cleaned up via the in-session SQL block before
`alembic upgrade head` applied 0018. The data loss was a single
duplicate — substantively zero — but the existence of the dup is
a faint signal that some past code path produced one. Worth a grep if
it ever resurfaces.
