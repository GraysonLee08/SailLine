# 2026-06-05 session

## What we worked on

Resolved the handoff's open item: **the pre-race route did not render on the
`/recording` screen**, and — per the user's "Google Maps" expectation —
**there was no live re-route while recording**.

Diagnosed both as one root cause: `useRouting` and `useRouteNotifications`
were instantiated per-screen with component-local state. The home screen
computed the route, opened the better-route SSE stream, and showed the
banner; navigating to `/recording` mounted fresh instances starting at
`route = null` with no SSE, so the plan vanished and no live updates arrived.

Fix: hoisted both hooks into a shared `RoutingProvider` (mirrors the existing
`RecorderProvider`, which exists for the same "must outlive a single screen"
reason). Both screens now read one instance keyed on the selected race id.

## Files changed

- **NEW** `mobile/src/routing/RoutingContext.tsx` — `RoutingProvider` +
  `useRoute()`. Wraps `useRouting` + `useRouteNotifications` keyed on
  `selectedRace.id` (read from `useRecorder()`), wires SSE accept →
  `applyAlternative` internally (consumers call `acceptAlternative()`), and
  clears stale route state when the race id changes.
- `mobile/app/_layout.tsx` — nested `<RoutingProvider>` inside
  `<RecorderProvider>`, above the router `Stack`.
- `mobile/app/(app)/index.tsx` — replaced local `useRouting` +
  `useRouteNotifications` with `useRoute()`; `BetterRouteBanner` now calls
  `routing.acceptAlternative()` / `routing.dismissAlternative`. Behaviour
  unchanged from the user's perspective.
- `mobile/app/(app)/recording.tsx` — consumes `useRoute()` (so
  `routing.route` is populated from the shared instance); added
  `BetterRouteBanner` to the top of the bottom stack; added a
  compute-on-mount fallback effect for the auto-start / crash-recovery paths
  where the user reaches `/recording` without computing on home; reads
  `useAutoRouteSetting` to drive the banner's auto-accept countdown.

## Decisions made and rationale

- **Lift state to a shared provider (vs. duplicating compute/SSE/banner onto
  `recording.tsx`).** User-approved. Fixes both gaps at the root and avoids
  re-introducing the per-screen fragility that caused the bug — i.e. avoids
  new tech debt. Side benefit: a single SSE connection now persists across
  Home ↔ Recording navigation instead of tearing down/reopening per screen.
- **Keep `compute()` user/race-day-triggered, not automatic in the
  provider.** Auto-computing for every browsed race would waste backend
  calls. The recording screen calls compute on mount only because reaching
  that screen means the user is committed to racing; the backend call is
  idempotent + Redis-cached (1h TTL) so it returns the existing route
  immediately.
- **Clear route on race-id change inside the provider.** Prevents a newly
  selected race from briefly showing the previous race's polyline. Navigation
  between Home and Recording does not change the race id, so the computed plan
  is preserved across that transition.
