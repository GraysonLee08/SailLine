# Session summary — 2026-05-24 — Platform pivot: native mobile (React Native/Expo)

## What we worked on

Analyzed an exported `track_points` dataset, diagnosed why on-water recording has been unreliable, and made a platform-direction decision: split SailLine into a **native mobile app** (on-water capture, routing, AI tactician) and the **existing web app** (management + pre-race + post-race review). Selected the mobile framework and recorded the decision as an ADR.

### Data analysis
- Reviewed `studio_results_20260524_2206.csv` — a `track_points` export, 1,521 rows across two sessions on 2026-05-15 (Chicago lakefront).
- Capture mechanics are sound: dense ~2 Hz sampling, position/speed/heading populated on nearly every row.
- But: speeds (0.05–2.8 kts) and path shapes confirm these were **on-foot tests**, not sailing. `wind_speed`, `wind_dir`, `gps_acc_m` empty on all rows. Session 2 had out-of-order timestamps (a -23s interval and a ~5-min gap).
- Plotted both tracks colored by speed (`track_plot_20260515.png` in the OneDrive workspace).

### Root-cause diagnosis
- The PWA cannot track GPS while the screen is locked — a fundamental browser limitation (`setTimeout`/geolocation throttled when backgrounded), not a bug. This is why recent tests "didn't work" and why auto-start (`useAutoStartRecorder`) doesn't fire when backgrounded.
- The 2026-05-14 Capacitor effort was **never completed**: the `lib/geolocation.js` adapter and `useTrackRecorder` rewire landed, but `frontend/android/` was never generated, no `@capacitor/*` deps are in `package.json`, and the screen-locked smoke test never ran.

### Decision
- Chose **React Native via Expo + EAS Build** over Flutter and over finishing Capacitor.
- Drivers: maximal reuse of existing JS client logic in a shared package; EAS Build ships iOS from Windows with no Mac (enables parallel iOS+Android); Transistorsoft `react-native-background-geolocation` (with Expo config plugin) for reliable background capture; mature `@rnmapbox/maps`.
- Repository approach: single **npm-workspaces monorepo** — `packages/shared` (single JS/TS source of truth) consumed by `frontend/` (web) and a new `mobile/` (Expo). `frontend/` stays put to avoid breaking Cloud Build paths.

## Decisions made and rationale
- **Native mobile, not finish-Capacitor.** Background reliability and map performance for a race-critical app justify true native over a webview wrapper.
- **React Native over Flutter.** Backend reuse is equal (both are REST/SSE clients), but RN reuses the existing JS client logic and keeps web+mobile in one language/shared package; Flutter would duplicate that logic in Dart permanently.
- **Expo + EAS Build.** The only practical path to ship iOS in parallel from a Windows-only, Mac-less setup.
- **Paid Transistorsoft plugin** — reverses the 2026-05-14 choice of the free community plugin; reliability matters more than the ~$300/platform cost for race capture.
