## Decisions & rationale

- **Transistorsoft is the capture engine only; the JS recorder owns queue/flush.**
  Its built-in HTTP autoSync posts the plugin's own location schema, not our
  batched `{gps:[...]}` shape, and threading hourly-expiring Firebase tokens
  through the native HTTP layer is fragile. Reusing the proven web queue/flush
  logic over AsyncStorage avoids a schema/auth mapping layer.
- **No CORS change.** Native RN `fetch` sends no `Origin` header, so the browser
  CORS middleware doesn't gate it. This contradicts the dev plan's "CORS for the
  mobile origin" line; only relevant if Expo *web* is ever used. Verify against
  the deployed API from the dev client.
- **Contract test, not a rewrite.** `test_telemetry.py` already covers the
  endpoint (18 tests). The real gap was a *shared wire-format* fixture + a
  validation test, so that's all that was added. "Known debt #2" is effectively
  retired.
- **GPS-only Phase 1.** IMU is a HUD feature (Phase 4); keeping it out de-risks
  the background-execution proof.

## Tech debt flagged

- Native builds still not in CI (carried from the ADR) — regressions caught only
  by manual device testing for now.
- AsyncStorage queue persists on every 1 Hz fix; fine at this rate, but revisit
  with debounced writes if it shows up in profiling.
- `react-native-background-fetch` dance — the real root cause documented for
  future-you: bg-geo declares `react-native-background-fetch: ~4.2.6`, but the
  4.2.x branch's Gradle requires `com.transistorsoft:tsbackgroundfetch:1.0.4`,
  an AAR that ships ONLY in bg-fetch's own `android/libs/`. Expo's
  settings.gradle uses `FAIL_ON_PROJECT_REPOS`, which ignores the project-
  level `maven { url "$projectDir/libs" }` declaration inside bg-fetch's
  build.gradle. bg-fetch's own Expo config plugin is a no-op stub (verified
  in source) so it doesn't register the repo at the settings level either.
  bg-geo's plugin only registers its own libs path. **Fix**: pin
  `react-native-background-fetch: ^4.4.0` as a direct dep so npm hoists 4.4.x
  at root — the 4.4.x line uses a newer tsbackgroundfetch artifact that
  resolves cleanly. Keep `"react-native-background-fetch"` in the plugins
  array (still a no-op, but matches Transistorsoft's documented setup).
  expo-doctor will warn about a duplicate background-fetch (root 4.4.x + bg-geo's
  nested 4.2.x); the warning is **load-bearing**, leave it.
- (resolved) `Development plan.docx` end-of-session ritual completed — new
  "Phase 1 — Background GPS capture (2026-05-25)" section appended covering
  scope, authentication pivot, end-to-end validation results, gotchas captured,
  and close-out items.
- **Google sign-in pivot**: started on `expo-auth-session/providers/google`,
  hit `Error 400: invalid_request` from Google's authorize endpoint despite
  correct Android client config (package `com.sailline.app`, SHA-1 matched).
  Diagnosed as expo-auth-session sending a redirect URI Google's Android
  OAuth client doesn't accept. Migrated to `@react-native-google-signin/`
  `google-signin` (native Play Services SDK) — no browser-redirect flow,
  Google matches calling app via package + SHA-1 at the OS level, the Web
  Client ID is only used as the Firebase id_token audience. Worked first
  try after the migration. Lesson: for Firebase + Google + custom dev
  clients, skip expo-auth-session entirely.
- **License env-var footgun**: `license: process.env.TRANSISTOR_LICENSE` in
  `app.config.js` writes the literal string "UNDEFINED" into
  AndroidManifest.xml when the env var is unset, which the runtime SDK
  then rejects ("LICENSE VALIDATION FAILURE — Invalid license key:
  UNDEFINED"). Fix: spread conditionally so the field is omitted when
  unset, letting the SDK fall to trial mode. Same trap will apply to the
  iOS license key when we get there.
- **SDK 54 → 56 drift**: a stray `npx expo install` (no args) bumped
  `expo`, `expo-auth-session`, and `expo-dev-client` to SDK 56 versions
  while `react-native` stayed at 0.81.5, causing `expo-modules-core`
  Kotlin compile errors in `Promise.kt`. Fix: pin everything to SDK 54
  ranges, delete `node_modules` and root `package-lock.json`, reinstall.
  Watch for this on future dep changes.
