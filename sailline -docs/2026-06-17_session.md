# 2026-06-17 Session — Recorder captured zero GPS points (stationary-state fix)

Diagnosed why the 2026-06-14 on-water race "Lady Skipper 6.14 - Race 1"
showed a live "LIVE" recording screen for ~81 minutes but recorded
nothing, then shipped the root-cause fix (code-complete, not yet
on-water verified).

## What we worked on

Investigated the failed recording from two Cloud SQL Studio exports
Grayson pulled (`race_sessions` row + the recorder debrief), traced it
through the mobile recorder and backend ingest, ruled out the obvious
suspects, found the real cause, and patched the Transistorsoft watcher.

## Root cause

The recorder ran 16:07:56 → 17:29:17 (~81 min) and captured **zero GPS
fixes**.

- The `race_sessions` row had empty `started_at`, `ended_at`,
  `mark_passes`, **and** `detector_state` while `start_at` was set. The
  backend writes `started_at = start_at` and `detector_state` on *every*
  telemetry batch it processes (`track_ingest.detect_and_persist_new_passes`
  / `_persist_quiet_state`), so all-empty ⇒ **zero telemetry batches ever
  reached `/api/races/{id}/telemetry`**. Not a backend bug.
- The recorder debrief confirmed capture-side: `points_captured=0`,
  `attempts=0`, ring buffer held only `start mode=js` and `imu on`. The
  JS queue stayed empty, so `flushNow()` early-returned every cycle
  (no upload was ever attempted).
- The serene "LIVE" UI is because `start()` sets `recording=true`
  unconditionally (useTrackRecorder.ts), decoupled from whether any fix
  arrives.

**Ruled out:** location permission (Grayson confirmed "Allow all the
time") and the Transistorsoft license (decoded the JWT in the manifest —
valid, bound to `com.sailline.app`, `core` entitlement, good through
build-stamp 2027-06-27; the "UNDEFINED → silent disable" trap did not
fire).

**Actual cause:** Transistorsoft boots into the STATIONARY state and only
emits locations once its motion-activity detector decides the device is
"moving." Nothing in `startWatcher` forced that transition.
`distanceFilter:0` / `pausesLocationUpdatesAutomatically:false` only
govern behaviour *while already moving*. On a sailboat — smooth, slow
motion the Android activity classifier doesn't reliably label as moving —
the plugin can sit stationary the whole race and never record a fix, with
no error raised. This also unifies the 2026-05-31 bursty-with-gaps
capture and the A4 "Speed/Track shows —" note: both are motion-state
symptoms.

## Files changed

- `mobile/src/recorder/backgroundGeolocation.ts` — fix 1:
  - `disableStopDetection: true` in the `geolocation` config block so a
    low-motion lull (head-to-wind, pre-start drift) can't pause capture.
  - `await BackgroundGeolocation.changePace(true)` immediately after
    `start()` to force the MOVING state so capture begins on the first
    fix. Best-effort (try/catch → `onError`) so a transient failure can't
    tear down an already-live watcher.
  - Docstring + inline notes documenting the 2026-06-15/17 rationale and
    the battery tradeoff.

## Decisions + rationale

- **Continuous GPS over motion-gated capture.** `disableStopDetection` +
  `changePace(true)` = always-on capture for the session. Higher battery,
  but correct for a bounded, foreground-service race recording — and the
  only reliable behaviour on a slow-moving boat.
- **`changePace(true)` is best-effort.** Tracking has already started by
  the time it runs; a changePace failure leaves us no worse than the
  pre-fix behaviour, so it must not reject the watcher promise.
- **Fix shipped in isolation first.** Grayson tests Wednesday; keep this
  build to the one variable so the on-water result is unambiguous.
