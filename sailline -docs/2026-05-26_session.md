## Decisions & rationale

- **Split Phase 2 into 2a (race-day minimum) + 2b (management parity).** Race-day doesn't need on-device boat/crew/race-creation UI — those happen on the web ahead of time. Native form screens (12-field boat editor, crew invites) are a substantial UI build that doesn't move tonight's deadline.
- **No new RN deps tonight.** No navigator (`expo-router`/`react-navigation`), no `expo-notifications`, no Mapbox. Kept the app as a single-file `App.tsx` screen state machine so the existing Phase 1 dev-client APK could pick up the changes via Metro fast-refresh — no EAS rebuild. Significant risk-reducer for a hard deadline.
- **Recorder hoisted to `AuthedShell`, not `RecorderScreen`.** The hook owns the GPS watcher lifetime; if it unmounted when the user navigated back to the picker, the recording would stop. Hoisting decouples lifetime from screen mount. Defensive: "Back" is disabled while recording, so the user can't strand the recorder on a null raceId.
- **`isRaced()` extracted to a single function.** Used by both the "Raced" pill and the Stats-button gating. Single source of truth prevents the two from disagreeing on the same race.
- **Filter/sort kept client-side.** No API change, no router change, no new endpoints. With race counts in the low double digits, client-side filtering is fine; server-side filtering is a follow-up if the list ever gets long.
- **Auto-start hook ported as a duplicate, not extracted to `@sailline/shared`.** Avoided touching the shared package + web app simultaneously (would have required synchronised vitest + RN verification, neither runnable in the build sandbox). Marked the duplication for a future consolidation session.
- **`formatRaceDate` duplicated web↔mobile** for the same reason.
