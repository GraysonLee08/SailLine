# 2026-06-04 — On-water feedback batch (Beer Can Race 4 post-mortem)

## What we worked on

Six issues from the 2026-06-03 Beer Can Race 4 on-water test. Five
mobile fixes plus one backend fix (Item 5 — the load-bearing one).
All six are landed; the only outstanding work is the on-water
re-verification.

## Items shipped

### Item 3 — SafeAreaView swap (Android status bar overlap)

**Symptom.** Hamburger chip and back chip rendered behind the Android
clock / battery icons.

**Cause.** `SafeAreaView` was imported from `react-native`. That
component is iOS-only and is a no-op on Android. Combined with
`<StatusBar translucent />`, the chips drew under the system bar.

**Fix.** Swapped to `SafeAreaView` from `react-native-safe-area-context`
(already a transitive dep via Gorhom). Required adding a `SafeAreaProvider`
at the root layout to feed the insets. The two call sites pass
`edges={["top"]}` / `edges={["bottom"]}` so the unrelated edge inset
doesn't pad them.

Files:
- `mobile/app/_layout.tsx` — added `SafeAreaProvider` wrap
- `mobile/app/(app)/index.tsx` — import swap + `edges={["top"]}`
- `mobile/app/(app)/recording.tsx` — same swap for both top + bottom rows

### Item 1 — Permission welcome card

**Symptom.** Users only saw the notifications permission prompt at
sign-in. Location was prompted lazily by Transistorsoft's
`BackgroundGeolocation.ready()` when recording started; activity
recognition was never explicitly requested. Users assumed the rest
were already configured.

**Fix.** New first-launch welcome card explains and requests three
permissions in sequence: notifications, Always-location, motion &
fitness. Honest copy distinguishes:

- Foreground location → blue dot + center-on-me work, but recording
  pauses with the screen locked.
- Background ("Always") → recording survives a pocketed phone (the
  load-bearing race-day case).
- Activity → battery savings only.
- Notifications → race-start reminders, missed-mark prompts, route
  alerts. Silently no-op without.

Gated on `@sailline.welcome.seen.v1` in AsyncStorage so it shows once
per install. Bumping the suffix re-shows after a release adds a new ask.

Files:
- `mobile/src/recorder/permissions.ts` (new) — wraps Transistorsoft's
  `BackgroundGeolocation.requestPermission()` and `Pedometer.requestPermissionsAsync()`
- `mobile/src/components/PermissionWelcomeCard.tsx` (new) — modal card +
  sequential prompt runner
- `mobile/app/_layout.tsx` — replaced `NotificationPermissionGate` with
  the new `WelcomeGate`

### Item 5 — Cross-batch detector state persistence (the big one)

**Symptom.** Mark 2 on Beer Can Race 4 was not auto-detected despite
a 1.1 m CPA and a textbook 5-sample depart pattern. User had to tap
manual. Marks 0, 1, 3 did detect correctly.

**Root cause.** `MarkRoundingDetector` traversal state (`_last_dist`,
`_min_dist`, `_min_ts`, `_departing`) was reset on every batch
because `detect_and_persist_new_passes` constructed a fresh detector
per call. The module docstring of `mark_rounding.py` already flagged
this as a known v3 gap.

Mobile's native uploader runs `autoSyncThreshold: 1`, so batches
arrive containing 1-3 samples each. The depart-confirm window (3
strictly-increasing samples after CPA) spans 3-4 batches in that
cadence. With `_last_dist` resetting to `None` at the start of every
batch, the `elif self._last_dist is not None and d > self._last_dist`
branch that increments `_departing` never fires. The detector
watches the target forever and never emits.

Marks 0, 1, 3 worked because they happened to coincide with larger
batches (offline catch-up flushes / brief connectivity drops).
Real-time detection was a coin flip dependent on upload cadence.

**Fix.** Three pieces:

1. `migration 0020_add_detector_state.py` — additive `detector_state
   JSONB` column on `race_sessions`. NULL is the "fresh traversal"
   sentinel. No backfill needed.
2. `MarkRoundingDetector.dump_state()` / `restore_state(state)` — JSONB-
   friendly snapshot of the running traversal. Constructor accepts a
   new `state=` kwarg that calls restore on init. Round-trip survives
   JSON encoding (asserted in tests).
3. `detect_and_persist_new_passes` — reads `detector_state` from
   `race_sessions` via the loader, restores on the detector, dumps
   after the batch, and persists it in the same UPDATE that already
   writes `mark_passes`. **Behavioural change**: every batch now hits
   the UPDATE (previously the no-new-pass case was a no-op). Cost is
   one row write per batch with a small JSONB column — negligible vs.
   the Mark-2-style miss the fix prevents.

Verified end-to-end with a fixture of the actual Beer Can Race 4
telemetry (4,543 points, 1 Hz). Two new pure-function tests:

- `test_beer_can_4_streaming_one_sample_batches_without_state_misses_marks`
  — replays the trace one sample per `feed_batch`, no state threading.
  Documents the bug; emits 0 passes.
- `test_beer_can_4_streaming_one_sample_batches_with_state_detects_all_marks`
  — same replay with `dump_state` / `restore_state` round-tripped through
  JSON between calls. Detects all 4 marks the boat actually sailed
  (the race was a DNF — marks 4 and 5 were never reached).

Plus three smaller unit tests covering the dump/restore contract and
the one-sample-batch failure mode in isolation. Existing tests in
`test_track_ingest.py` were updated for the new always-write
semantics and the additional `detector_state` column in the loader
shape; existing tests in `test_telemetry.py` and `test_tracks_router.py`
were updated for the new `_race_row` fixture shape.

### Item 4 — Auto-start countdown stale

**Symptom.** Mobile auto-start countdown showed "fires in 2h 8m" while
web showed "Starts in 00:55:56" at the same wall-clock time, and the
mobile value never adjusted regardless of when the user looked.

**Cause.** `useAutoStartRecorder` set `msUntilFire` once at effect
mount and never ticked it down. The render in `RaceDetailSheet` was
rendering a frozen snapshot of whatever `Date.now()` was when the
effect first ran.

**Fix.** Added a 1 Hz `setInterval` inside the arm path that recomputes
`armAt - Date.now()` and pushes it to state. Clears on cleanup
alongside the existing fire `setTimeout`. The recompute is from the
wall-clock target (`armAt`) not by decrementing the prior value, so
a backgrounded JS runtime doesn't drift relative to real time.

Also added a `__DEV__`-gated one-shot log of the parsed `startAt` so
the next on-water test can confirm whether there's an additional
parse-time discrepancy (the 1h 17m delta between mobile and web at
the same moment hints at a stale cache or timezone parse drift that
the snapshot bug masked).

Files:
- `mobile/src/recorder/useAutoStartRecorder.ts`

### Item 2 — Map taps not registering after sign-in

**Symptom.** Immediately after first sign-in, the map screen ignored
all taps. Workaround that fixed it: enter split-screen and exit it.

**Cause (working hypothesis, NOT verified — couldn't reproduce in the
sandbox).** rnmapbox's Android view occasionally fails to wire up
touch routing on first mount until an external relayout forces a
re-measure. Split-screen reliably triggers that re-measure via
`onConfigurationChanged`. The community-known fix is to issue a no-op
`setCamera` shortly after mount, which forces the SDK to recompute
its viewport and incidentally rebinds touch dispatch.

**Fix.** Added a mount-time effect to `MapCanvas` that, 800 ms after
mount, issues `camRef.current?.setCamera({ animationDuration: 0,
padding: ... })`. Visually a no-op (no zoom or center change); side
effect is a native invalidate that fixes touch routing in the
suspected failure mode.

**Status.** Needs on-water verification on a fresh sign-in. If the
nudge alone doesn't fix it, the next step is to ALSO conditionally
mount `AppMenuSheet` only when open (instead of mounting at
`index={-1}`) — Gorhom's backdrop has occasionally been seen to
retain touch-stealing behaviour even when "disappeared." Documented
as a follow-up.

Files:
- `mobile/src/components/MapCanvas.tsx`

## Decisions made and rationale

- **JSONB for detector_state, not per-field columns.** Detector state
  shape is an implementation detail of the algorithm; a v4 detector
  with extra fields (e.g. recent-bearing history) shouldn't need
  another migration. JSONB is a hot-path read + write but a single
  column update vs. several is cheaper.
- **Always-write the UPDATE in track_ingest.** Pre-0020 the quiet
  no-pass case skipped the UPDATE entirely. Post-0020 we always
  write so the next batch can restore traversal state. The extra
  ~negligible cost beats the Mark-2-style misses, which are silent
  failures from the user's perspective.
- **Bottom-sheet welcome card, not a dedicated route.** Sign-in →
  modal card → tap done → land on map matches the OS-prompt-stack
  flow the user is already familiar with. A dedicated route would
  add a navigation step that's only relevant on first install.
- **Layers FAB does NOT include a base-map style toggle yet.** Theme
  picker (light/dark) is already in Settings; satellite-vs-monochrome
  is a separate piece that needs Mapbox Studio work to publish the
  custom styles. Deferred to a follow-up so the Layers panel ships
  this week.
- **1 Hz countdown tick, not 100 ms.** A second's resolution is what
  the UI shows ("fires in 2h 8m"); polling faster wastes cycles on a
  static-text update.
- **Mount-time touch nudge, not a key-bump remount.** Forcing
  MapCanvas to remount via a key would also reload the map style and
  burn a Mapbox API call. The no-op `setCamera` achieves the same
  layout-invalidate without the cold-start cost.

## Technical debt flagged

- **`AppMenuSheet` index={-1} as a "hidden" mount.** If item 2's
  touch-nudge fix doesn't fully resolve, the sheet's permanent mount
  is the next suspect. The fix would be conditional mounting +
  `useState<boolean>` open flag, which makes the existing
  forwarded-ref `open()` / `close()` API a leaky abstraction.
  Worth doing if it turns out to be load-bearing.
- **Detector state migration on in-flight races.** The new column
  defaults to NULL on existing rows. A race that's in the middle of
  the v2-era no-state code path when 0020 applies will continue
  in the new path with a fresh traversal — no data loss, but the
  first post-deploy batch may take one extra batch to re-accumulate
  the depart-confirm count for the current target mark. Acceptable.
- **`ActualRouteLayer` Douglas-Peucker thinning.** Still flagged from
  2026-06-03 — caps at 5,000 points and drops the oldest. A 3-hour
  race at 1 Hz loses the first ~7k points on the displayed line.
- **No mobile test infra.** Carryover. `useLayerSettings`,
  `permissions.ts`, the new card component — all worth unit tests.
  Setting up vitest or jest in the mobile workspace is its own scope.
- **TypeScript verification gated on Windows.** Sandbox bash mount of
  `E:\` is unreliable for tsc / vitest reads; build-time checks must
  run from PowerShell.
- **Mobile recorder log dev-only `console.log` in `useAutoStartRecorder`.**
  Gated by `__DEV__` so production builds drop it, but if Metro ever
  preserves console in release this would surface. Worth migrating to
  the `recorderLog` ring buffer next time we touch this file.
