## Decisions and rationale

**Removed the Directions FAB.** The race detail sheet already has a Recompute button in its header, and the FAB cluster's Directions FAB called the same handler. Duplicating it on the map surface added visual noise without earning the user a new capability. Keeping Start + Minimize because those are race-flow actions the user wants reachable while interacting with the map.

**Cycle compassMode off→on to fix Locate-me in heading-up.** Mapbox's `<Camera followUserLocation={true}>` silently unbinds its internal follow after the user pans, but the React prop remains true. Any imperative `setCamera()` we make in that state gets clobbered by the stale-but-still-bound declarative follow on the next layout pass. Cycling the state forces the Camera to re-mount the binding with FollowWithHeading. Mirrors the existing setTimeout dance in `toggleCompass`. Used a ref because `useImperativeHandle(deps=[])` would otherwise close over a stale value.

**Modal+FlatList picker over Alert.alert.** Alert tops out at ~8 useful actions before it overflows the screen; the COURSE_FAMILIES list is ~80 entries. A Modal with pageSheet presentation + FlatList covers both small (boat classes, 8 items) and large lists cleanly with one component.

**Webapp editor refit when count grows, not on coord edit.** A naive "always refit" would jerk the map every keystroke commit and every marker drag. Tracking the last-fit count lets us refit on add-a-mark (the user wants to see their growing course) without disrupting mid-edit.

**parseCoord regression test added in `packages/shared`, not webapp.** Mobile imports the same module via `@sailline/shared`, so a shared-package test covers both platforms with one suite.

## On-water race finding (Colors (Bravo), 2026-05-30 noon CDT)

Race did not save mark passes, did not auto-stop, and did not produce stats. Three confounding bugs surfaced at once:

1. **Mark-detection radius too tight for distance racing.** `mark_rounding.py` uses 50 m intermediate / 75 m final. Distance race past Wilson Crib / Harrison-Dever / Purdue Buoy — typical boat path is 100–300 m off the nav structure. With zero passes detected, auto-stop can never fire because it triggers on rounding the final mark. (Task #6.)
2. **No manual stop on webapp with `RECORDING_ENABLED=false`.** Recorder hooks still arm in the background (pragmatic-gate design from yesterday), but the Record/Stop UI is gated off. So a stuck recording can't be ended manually. Either un-gate the Stop button or rip out the gate once mobile is ready. (Task #7.)
3. **No delete-race UI on either platform.** Colors (Alpha) couldn't be cancelled before the race; sat as a phantom alongside the actual race. DELETE endpoint existence not verified yet. (Task #8.)

Also flagged but not yet diagnosed: Alpha's `started_at` was also stamped at gun time even though only Bravo was the selected race. Either backend is backfilling for any race with matching user_id, or telemetry briefly hit Alpha before the user switched. Needs reading `track_ingest.py:225-280` against the recorder's race-id binding. (Task #9.)

`started_at` being set is itself a *positive* signal — backend only writes it when telemetry first arrives (`track_ingest.py`). So the GPS recorder *was* uploading points. The problem is downstream: detection didn't catch any mark crossings.

## Tech debt flagged (2026-05-30)

**Mark-detection radius is fixed at 50 m globally.** Hard-coded constant in `mark_rounding.py` doesn't account for race mode. Distance races, harbour entrances, and any course where the mark is a nav structure (not a buoy you'd touch) will silently fail to detect passes.

**Webapp `RECORDING_ENABLED` gate has surfaced its first real cost.** Yesterday we accepted "dead-but-mounted recorder hooks" as a known trade-off. Today's race shows that the user can run a recorder with no UI feedback and no Stop button — strictly worse than either "no recorder at all" or "full recorder UI." The gate needs to either (a) gate the *hook arming* too, not just the UI, or (b) keep the Stop button visible regardless.

**Picker overflow guard.** The Modal+FlatList picker handles long lists, but COURSE_FAMILIES gives ~80 unbucketed options. Should display by family group (currently just prepends family label to each option). Acceptable for v1; revisit when the list grows past 100.

**`useImperativeHandle(deps=[])` closures.** MapCanvas's compass+locate handlers have to read latest state via refs because the imperative handle is memoized with empty deps. Pattern is correct but error-prone — easy to write a new handler that closes over stale state. Worth a comment-block standard at the top of the imperative-handle definition.
